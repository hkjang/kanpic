## 릴리즈 요약

v0.34.0은 워크북 자동화를 미리보기부터 실행·재시도·스케줄링·Undo까지 일관된 서버 권위 계약으로 강화한 안정성 및 사용성 릴리즈입니다. 저장 대기 편집과 오래된 미리보기로 인한 오작동을 차단하고, 응답 유실이나 다중 인스턴스 경쟁 상황에서도 같은 자동화가 중복 적용되지 않도록 복구 흐름을 보강했습니다.

`024_automation_rate_admission.sql` 데이터베이스 마이그레이션과 수동 실행 API 변경이 있습니다. 필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나이며, `BOOTSTRAP_ADMIN_ID`·`BOOTSTRAP_ADMIN_PASSWORD`와 Keycloak Confidential Client의 `client_secret` 설정도 그대로 사용할 수 있습니다.

## 검증된 미리보기와 안전한 실행

- 자동화 미리보기 전에 저장 대기 셀 편집과 전송 대기 작업을 동기화하고 최신 워크북 버전을 다시 확인합니다.
- 미리보기에 자동화 이름·revision·작업 스냅샷과 워크북 기준 버전을 고정해, 정의나 데이터가 바뀐 오래된 승인을 실행하지 않습니다.
- 수동 실행은 미리보기의 `automation_revision`과 `base_version`을 각각 `expected_revision`, `expected_base_version`으로 제출해야 하며 불일치는 409로 중단됩니다.
- 이미 원하는 상태인 미리보기는 오류가 아닌 **변경 없음**으로 표시하고 불필요한 워크북 버전 생성을 막습니다.
- 값의 숫자·불리언 정규화, 수식의 유니코드 공백과 변동 함수 판별, 최대 범위 및 실행 스냅샷 크기 검증을 강화했습니다.

## 정확히 한 번 실행과 장애 복구

- 생성·실행·Undo의 멱등 키를 성공할 때까지 유지하고 응답 유실 후 같은 키로 재시도하면 기존 실행에 안전하게 합류합니다.
- 셀 적용 뒤 상태 응답이 유실된 모호한 실패는 `running` 상태로 보존하고 동일한 내부 작업 키로 복구해 중복 셀 작업을 만들지 않습니다.
- 자동화 revision 확인과 실행 접수를 같은 트랜잭션에서 잠그고, 워크북 단위 advisory lock으로 시간당 실행 한도 판정과 실행 행 생성을 원자화했습니다.
- 제한 때문에 거부된 예약 실패는 시간당 실행 수에 포함하지 않으며, 예약 실행이 아직 복구 중이면 다음 실행 시각을 앞당기지 않습니다.
- 실패 실행 재조회, 삭제된 생성 키 재사용, 트리거 유일 키 경쟁과 Undo 재시도의 상태 처리를 명확히 했습니다.

## 권한·트리거·운영 안정성

- REST와 MCP 자동화 권한 검사를 fail-closed로 통일하고, 여러 리소스 ID를 섞어 다른 워크북 권한을 우회할 수 없도록 모두 검증합니다.
- 정렬, AI 변경 승인과 Workbook Agent 승인으로 발생한 셀 작업도 셀 변경 자동화 트리거에 전달합니다.
- 중복 실행 결과는 협업 이벤트를 다시 발행하지 않으며, 요청 취소 뒤에도 접수된 트리거는 제한된 백그라운드 컨텍스트에서 마무리합니다.
- 서버 종료 시 자동화 스케줄러와 AI 보존 작업이 끝날 때까지 기다려 로거·DB 풀이 먼저 닫히는 종료 경쟁을 제거했습니다.

## 자동화 패널 사용성

- 로딩·오류·재시도 상태와 접근성 레이블을 추가하고 시트 이름이 포함된 범위 표시와 더 읽기 쉬운 조작 버튼을 제공합니다.
- 미리보기 뒤 워크북 버전 또는 자동화 revision이 어느 방향으로든 달라지면 즉시 오래된 상태로 표시합니다.
- 네트워크·5xx처럼 결과가 모호한 실행만 같은 키로 재조회하며, 확정적인 4xx 오류는 새 검증 흐름을 시작하도록 구분합니다.
- 자동화 실행 뒤 현재 선택과 편집기 Undo 이력을 유지하고, 보기 전용 사용자는 자동화 메뉴를 실행할 수 없습니다.

## 업그레이드 안내

- 서버 시작 시 `024_automation_rate_admission.sql`이 자동 적용되며 기존 실행 이력은 접수된 실행으로 유지됩니다.
- 자체 REST/MCP 클라이언트는 `:test` 응답의 `automation_revision`과 `base_version`을 수동 실행 요청에 반드시 전달해야 합니다.
- 응답을 받지 못한 실행을 재시도할 때는 새로운 멱등 키가 아니라 최초 요청과 같은 키를 사용해야 합니다.
