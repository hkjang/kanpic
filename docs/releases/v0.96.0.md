## 릴리즈 요약

v0.96.0은 **자동화가 조용히 죽는 세 가지 경우**를 고칩니다. 트리거 네 가지를 실제로 돌려 보다 찾았습니다.

마이그레이션은 없습니다. 필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나입니다.

## 꺼져 있는 줄 모르는 자동화

자동화 실행은 관리자 설정이고 **기본값이 꺼짐**입니다. 그런데 워크북 쪽에는 그 사실이 어디에도 없었습니다. 자동화를 만들고, 검증을 눌러 초록색 미리보기까지 받은 다음, 실행을 눌러야 비로소 "관리자 화면에서 자동화를 활성화하세요" 가 돌아왔습니다.

셀 변경·일정·웹훅 트리거는 그 알림조차 없었습니다. 만들어 두면 카드에 **사용 중**이라고 적혀 있고 일정 카드에는 다음 실행 시각까지 표시되지만, 실제로는 아무것도 돌지 않았습니다.

이제 자동화 목록이 실행 가능 여부를 함께 내려줍니다. 꺼져 있으면 패널 위쪽에 그 사실과 켜는 위치를 안내하고, 실행 단추를 비활성화하며, 돌지 않을 일정의 다음 실행 시각은 감춥니다. 정의를 만들고 검증하는 것은 그대로 됩니다.

## 서버 로그에만 남던 실패

셀 변경 트리거가 실패하면 그 실패는 **서버 로그에만** 남았습니다. 실행 이력은 비어 있었고, 그 셀을 편집한 사람은 아무것도 보지 못했습니다.

실행 행을 만들기 전에 거절된 경우였기 때문입니다. 예를 들어 관리자가 실행당 셀 한도를 자동화를 만든 뒤에 낮추면, 그 자동화는 편집할 때마다 거절되지만 어디에도 흔적이 남지 않았습니다.

이제 그런 거절도 `failed` 실행과 사유를 남깁니다. 실행 이력에서 보이고, 목록 카드에는 마지막 실행이 실패했다는 표시가 시각·사유와 함께 붙습니다. 이후 실행이 성공하면 표시는 사라집니다. 시간당 한도 초과처럼 편집마다 반복되는 거절은 자동화별로 시간당 한 행으로 합쳐 한도가 스스로를 무너뜨리지 않게 했습니다.

셀 변경 트리거는 응답을 쓰기 전에 동기적으로 돌기 때문에, 실패는 그 편집의 응답에 실려 돌아옵니다. 편집한 사람에게는 화면 왼쪽 아래로 **자동화가 실패했습니다**와 사유를 바로 알립니다. 편집 자체는 저장되었고 실패한 것은 뒤따르던 자동화뿐이라는 점도 함께 적었습니다.

## 사유 없는 실패

실행 이력에 남던 `failed` 행도 사유가 비어 있었습니다. 실행 행을 넣는 SQL이 `error_message` 열을 빠뜨리고 있었고, 예약 실행 실패도 같은 경로를 씁니다. 화면에는 **실패**라고만 뜨고 왜인지는 알 수 없었습니다. 이제 사유가 함께 저장됩니다.

## 확인만 하고 지나간 것

실행 자체는 멀쩡했습니다. 실행을 켠 뒤 네 가지 트리거를 모두 실제로 돌려 확인했습니다. 셀 변경은 감시 범위를 건드리자 바로 수식을 다시 계산했고, `* * * * *` 예약은 스케줄러가 정각에 한 번 실행했으며, 웹훅은 API 키로 인증해 payload digest만 남기고 값을 썼습니다. 자동화의 셀 쓰기도 보호 범위 검사를 그대로 통과합니다.

## 검증 결과

- E2E 두 가지를 남겼습니다. 실행이 꺼져 있을 때 패널이 그렇게 말하고 실행 단추를 잠그는지, 셀 변경 자동화가 실패했을 때 편집자에게 알리고 실행 이력에 사유가 남는지 확인합니다.
- 고치기 전 번들과 서버에서 두 시나리오가 모두 실패하는 것을 확인했습니다.
- 통합 테스트를 하나 더했습니다. 성공 → 한도 축소로 실패 → 한도 복구로 회복까지 돌려 실행 이력과 목록 표시가 함께 따라오는지 확인합니다.
- `go vet ./...`, `go test ./...`, PostgreSQL 통합 테스트, React/Vitest 267개 테스트, TypeScript 타입 검사, Vite 프로덕션 빌드, Playwright E2E를 통과했습니다.
