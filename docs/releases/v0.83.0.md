## 릴리즈 요약

v0.83.0은 **정렬을 21배 빠르게 하고 정렬할 수 있는 크기를 여섯 배로 늘립니다.** 5만 행 시트의 읽기 성능을 재다가, 정렬만 크기의 제곱에 비례해 느려지고 있는 것을 찾았습니다.

마이그레이션은 없습니다. 필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나입니다.

## 읽기 쪽 측정

5만 행 × 3열 시트에서 잰 값입니다. 대부분은 문제가 없었습니다.

| 동작 | 시간 |
| --- | --- |
| 화면에 보이는 범위 읽기 | 5 ms |
| 필터 평가(5만 행 중 12,500행 통과) | 356 ms |
| 시트 통계 | 133 ms |
| CSV 내보내기 (1.3 MB) | 369 ms |
| XLSX 내보내기 (1.0 MB) | 586 ms |
| **정렬** | **거부됨** |

정렬만 아예 되지 않았습니다. 한도가 10,000셀이라 열이 세 개면 3,300행이 상한이었습니다.

## 제곱에 비례하던 정렬

한도를 올려 보니 이유가 드러났습니다.

| 정렬 크기 | 이전 |
| --- | --- |
| 5,000행 (15,000셀) | 2.5초 |
| 10,000행 (30,000셀) | 9.1초 |
| 20,000행 (60,000셀) | 33.6초 |

두 배마다 네 배입니다. 프로파일러가 한 곳을 가리켰습니다. 시간의 90%가 `clearSpillCells` 였습니다.

셀을 덮어쓸 때, 그 셀이 배열 수식의 원본이었다면 그것이 펼쳐 놓은 결과도 함께 지워야 합니다. 그 결과 셀들을 찾으려고 **쓰는 셀마다 시트 전체를 훑고** 있었습니다. 15,000개를 쓰면 시트를 15,000번 훑습니다.

펼쳐진 셀을 원본 주소별로 묶은 색인을 **한 번** 만들어 두고 찾아보게 바꿨습니다.

| 정렬 크기 | 이전 | 이후 |
| --- | --- | --- |
| 5,000행 | 2,469 ms | 368 ms |
| 10,000행 | 9,067 ms | 768 ms |
| 20,000행 | 33,581 ms | 1,597 ms |

제곱이 아니라 정비례로 바뀌었습니다.

## 정렬 한도

정렬은 붙여넣기와 성격이 다릅니다. 편집을 이어서 하는 것이 아니라 이미 가진 데이터에 대한 한 번의 동작이므로, 자체 한도 **60,000셀** 을 갖습니다. 열이 세 개면 20,000행, 다섯 개면 12,000행입니다.

한도를 넘으면 이제 몇 셀까지인지와 **그것이 몇 행인지** 를 함께 알려 줍니다. 셀 수만 알려 주고 열 수로 나누게 하는 것은 불친절합니다.

## 검증 결과

- 프로파일러로 원인을 짚었고, 고친 뒤 저장소 계층과 서버 양쪽에서 다시 쟀습니다.
- 배열 수식의 원본을 덮어쓰면 펼쳐진 결과가 사라지는지 확인하는 테스트를 더했습니다. 빨라진 것이 일을 덜 해서가 아니어야 합니다.
