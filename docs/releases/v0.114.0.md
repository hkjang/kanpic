## 릴리즈 요약

v0.114.0은 선택한 범위를 **프레젠테이션으로** 만듭니다. **데이터 › 프레젠테이션 만들기…** 를 누르면 표가 표지·지표·차트·상세 표·시사점이 있는 슬라이드가 되고, PPTX로 내려받을 수 있습니다.

핵심은 셀을 넘기지 않는다는 것입니다. kanpic이 먼저 범위의 **뜻** 을 정하고, 프레젠테이션 서비스는 그 뜻을 그립니다.

마이그레이션 `033_presentations.sql` 이 하나 늘었습니다. 서버 기동 시 자동 실행됩니다. 기능은 기본적으로 꺼져 있으며 관리자가 `presentation.*` 설정을 채워야 켜집니다.

## 스프레드시트가 아는 것을 넘겨야 한다

이런 표가 있다고 하겠습니다.

| 부서 | 매출 | 전년대비 | 목표달성률 |
| :--- | ---: | ---: | ---: |
| 영업1 | 120억 | +15% | 108% |
| 영업2 | 95억 | -3% | 91% |
| 영업3 | 110억 | +8% | 103% |

셀을 그대로 넘기면 받는 쪽은 열두 개의 문자열을 봅니다. 어느 열이 이름이고 어느 열이 값인지, `120억` 이 숫자인지 글자인지, 91%가 좋은 소식인지 나쁜 소식인지 다시 알아내야 하고, 알아낼 근거는 kanpic보다 적습니다.

그래서 kanpic이 먼저 정합니다.

- **모양**: 이름 열 + 숫자 열이므로 항목별 비교, 막대 차트.
- **단위**: `120억` 은 120이라는 숫자에 단위가 붙은 것. 차트는 120으로 그리고, 합계는 **325억** 이라고 적습니다. 단위를 잃고 "325" 라고만 쓰면 슬라이드가 무엇이 325인지 말하지 않습니다.
- **열의 노릇**: `전년대비` 와 `목표달성률` 은 둘 다 백분율이고 하는 말이 다릅니다. 앞의 91%는 그냥 낮은 값이지만 뒤의 91%는 **목표 미달** 입니다.
- **할 말**: 그래서 표지의 첫 줄이 "영업2의 목표달성률이 91%로 목표에 못 미칩니다" 가 되고, 지표 타일의 맨 앞자리도 그것이 차지합니다.

이 문장들은 전부 숫자에서 계산해 만듭니다. AI 제공자가 없어도 나오고, 없는 사실을 지어내지 않습니다. **목표를 모두 넘긴 표에서는 "목표 미달" 이라고 쓰지 않습니다** — 가장 낮은 달성률도 좋은 소식이면 할 말이 아닙니다.

## 범위의 모양이 슬라이드를 정한다

| 범위 | 슬라이드 |
| :--- | :--- |
| 이름 열 + 숫자 열 | 막대 차트 |
| 날짜 열 + 숫자 열 | 선 차트 |
| 100%로 모이는 백분율 | 비중 |
| 두 항목 | 비교 카드 |
| 숫자 네 개 이하 | 지표 타일 |
| 열이 많거나 열두 행을 넘는 표 | 표 |

`1월` 은 시간이고 `18개월` 은 기간입니다. 둘 다 "월" 로 끝나지만 앞은 가로축이고 뒤는 값이어서, 섞으면 추이 차트가 뒤집힙니다. 달력의 한 칸으로 읽는 범위(1~12월, 1~4분기, 1900~2200년)를 따로 두었습니다.

## 미리보기와 실제가 다를 수 없다

대화 상자의 미리보기는 **서버가** 만듭니다. 화면이 따로 그리지 않으므로, 보이는 구성과 만들어지는 덱은 같은 코드에서 나옵니다. 미리보기 동안에는 프레젠테이션 서비스를 부르지 않습니다 — 제목을 고쳐 보는 동안 남의 계정에 덱이 쌓이면 안 됩니다.

**이 범위를 이렇게 읽었습니다** 에 판단이 그대로 보입니다. 잘못 읽었으면 만들기 전에 알 수 있습니다.

## 다른 제품으로 바꿔 낄 수 있다

kanpic 안에 프레젠테이션 제품 이름이 흩어지지 않게 했습니다.

```
Presentation Service ──> PresentationProvider (인터페이스)
                              └── Ptium (지금 있는 유일한 구현)
```

`internal/presentation` 은 덱을 뜻으로만 다루고, 어느 제품에도 기대지 않습니다. Ptium을 아는 코드는 `internal/presentation/ptium` 한 곳뿐이고, 그 이름이 나오는 배선은 서버 기동 코드의 한 줄입니다. 다른 도구를 붙이는 일은 편집기·API·분석기를 고치는 일이 아니라 패키지를 하나 더 두는 일입니다.

Ptium에는 슬라이드를 **글로 쓰는 언어** 가 있어서, 프롬프트로 생성을 맡기지 않고 덱을 직접 적어 보냅니다. 이미 아는 숫자를 모델에게 다시 쓰게 하면 틀릴 기회만 생깁니다.

## 만든 덱은 워크북에 매인다

덱은 프레젠테이션 서비스의 **공용 계정** 아래 만들어집니다. kanpic이 어느 워크북에서 나온 덱인지 기억하지 않으면, 로그인한 누구나 남의 자료로 만든 덱을 내려받을 수 있습니다.

그래서 `presentations` 표에 원본 워크북·시트·범위와 그때의 워크북 버전을 적습니다. 내려받기는 그 워크북의 읽기 권한으로 판정하고, kanpic이 만들지 않은 덱은 누구에게도 내주지 않습니다. 같은 기록이 나중에 **원본이 바뀌었는지** 를 말해 줍니다.

브라우저는 프레젠테이션 서비스를 직접 부르지 않고 API Key도 받지 않습니다. 요청은 항상 kanpic 서버를 거칩니다.

## 관리자 설정

| 설정 | 내용 |
| :--- | :--- |
| `presentation.enabled` | 기능 사용. 꺼져 있으면 메뉴에 항목이 나오지 않습니다 |
| `presentation.base_url` | 프레젠테이션 서비스 주소 |
| `presentation.api_key` | 서비스 API Key (암호화 저장). `presentations:read` 와 `presentations:write` 만 있으면 됩니다 |
| `presentation.timeout_seconds` | 요청 제한 시간 (기본 60초) |
| `presentation.default_template_id` | 기본 디자인 |
| `presentation.max_cells` | 한 덱이 읽을 최대 셀 수 (기본 5,000) |

## 함께 고친 것

에이전트용 MCP 조건부 서식 스키마를 넓히면서 확인한 것과 같은 종류의 문제가 하나 더 있었습니다. 프레젠테이션 경로를 만들며 기존 `workbookIDForSheet` 가 **모든 워크북을 훑는** 방식인 것을 보았습니다. 새 코드에서는 색인을 쓰는 `WorkbookIDForResource` 를 씁니다. 기존 함수는 이번에 손대지 않았습니다.

## 알려진 한계

- 원본이 바뀌었는지는 기록해 두지만, 아직 **다시 만들기** 버튼은 없습니다. 워크북 버전은 하나짜리 계수기여서 "바뀌었을 수 있다" 까지만 말할 수 있습니다.
- 덱을 만드는 동안 화면이 기다립니다. 슬라이드가 많아지면 작업(Job) 방식이 필요합니다.
- 프레젠테이션 서비스의 MCP는 아직 쓰지 않습니다. 지금은 결정적인 경로(REST)만 있습니다.

## 검증 결과

- 사용자가 준 것과 같은 표로 분석기를 시험합니다: 단위가 붙은 값을 숫자로 읽는지, `전년대비` 와 `목표달성률` 을 다르게 보는지, 목표를 모두 넘긴 표에서 없는 문제를 지어내지 않는지, 합계가 단위를 유지하는지.
- 날짜 축과 기간을 가르는 경계를 표로 시험합니다 — `12월` 은 시간, `13월` 과 `18개월` 은 값.
- 숫자 위의 숫자를 머리글로 오해하지 않는지 봅니다. 오해하면 자료 한 줄이 통째로 사라집니다.
- 권한을 시험합니다: 만든 사람은 내려받고, 워크북에 권한이 없는 사람은 만들 때도 내려받을 때도 거절당하고, kanpic이 모르는 덱 번호는 서비스에 닿기 전에 막힙니다.
- 미리보기가 프레젠테이션 서비스를 부르지 않는지 확인합니다.
- 브라우저 E2E로 메뉴 → 대화 상자 → 만들기 → 내려받기를 끝까지 돌립니다. 서비스가 설정되지 않은 환경에서는 **메뉴에 항목이 없는 것** 을 확인합니다.
- 실제로 도는 Ptium을 상대로 전 과정을 돌려 5장짜리 PPTX가 나오는 것과, 슬라이드가 의도대로 그려지는 것을 그림으로 확인했습니다.
- `go vet ./...`, `go test ./...`, PostgreSQL 통합 테스트, React/Vitest, TypeScript 타입 검사, Vite 프로덕션 빌드, Playwright E2E를 통과했습니다.
