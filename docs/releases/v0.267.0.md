# v0.267.0

이번 릴리즈는 접수된 세 가지를 고칩니다. 둘은 편집기의 가장 기본적인
키보드 조작이고, 하나는 MCP 로 kanpic 을 쓰는 에이전트가 셀을 고치지 못하던
문제입니다.

| # | 현상 | 원인 | 이제 |
| --- | --- | --- | --- |
| 1 | `Ctrl + A` 를 누르면 화면이 멈추고, 기다려도 데이터가 선택되지 않음 | 상태 표시줄 요약이 시트 전체(약 33억 칸)를 한 칸씩 돌았습니다 | 멈추지 않습니다. 처음 누르면 **데이터 표 전체**, 다시 누르면 시트 전체 |
| 2 | `Ctrl + 방향키` 가 빈 칸이 없는데도 데이터 중간에서 멈춤 | 편집기는 화면에 보이는 행만 들고 있어, 화면 밖을 빈 칸으로 보았습니다 | 서버에 저장된 모든 행을 보고 끝을 찾습니다 |
| 3 | MCP 로 셀 쓰기·서식·자동화가 안 됨 | 쓰기 도구의 인수 목록에 `cells`·`row`·`column` 이 빠져 게이트웨이가 버렸고, 좁힌 토큰은 자기 워크북에도 쓸 수 없었습니다 | 인수가 그대로 도착하고, **자기 소유 워크북은 기본으로 쓸 수 있습니다** |

## `Ctrl + A` 가 멈추지 않고, 데이터 표부터 고릅니다

선택한 범위의 합계·평균·개수는 상태 표시줄 오른쪽에 나옵니다. 이 요약은
선택이 10만 칸을 넘으면 서버에서 값을 읽어 오지 않는데, 그때도 **선택한
사각형의 주소를 하나씩 돌며** 빈 칸을 세고 있었습니다. 시트 전체는
200,000 행 × 16,384 열, 약 33억 개의 주소이고, 브라우저 탭이 몇 분씩
응답하지 않았습니다. 기다린 끝에도 "선택 3,276,800,000셀" 이라는 말만 남고
데이터를 복사할 수는 없었습니다.

이제 요약은 실제로 있는 셀만 돌고, 너무 큰 선택은 아예 세지 않습니다. 그리고
`Ctrl + A` 는 엑셀·구글 시트처럼 움직입니다.

- **처음 누르면** 활성 셀을 둘러싼 데이터 표 전체를 고릅니다. 화면에 보이지
  않는 행까지 서버가 저장된 행을 보고 정합니다. 3,000행 표의 B10 에서 누르면
  `A1:B3000` 이 선택되고, 합계도 3,000행 전체의 합계입니다.
- **한 번 더 누르거나**, 주변에 데이터가 없는 칸에서 누르면 시트 전체를
  고릅니다. 이때도 편집기는 멈추지 않습니다.
- `Ctrl + Shift + A`(데이터 영역 선택)도 같은 서버 기준을 씁니다. 전에는
  화면에 들어온 행만으로 영역을 정했습니다.

메모 달기도 선택한 칸마다 화면용 사본을 만들기 때문에, 시트 전체를 고른
채로 메모를 달면 같은 식으로 멈췄습니다. 서식·붙여넣기처럼 한 번에
10,000칸까지로 막고, 넘으면 그렇다고 알려 줍니다.

## `Ctrl + 방향키` 가 데이터의 진짜 끝으로 갑니다

편집기는 큰 시트를 다루려고 화면에 보이는 행만 서버에서 읽어 옵니다. 그런데
`Ctrl + ↓` 는 그 읽어 온 셀만 보고 끝을 찾았으므로, 화면 아래로 이어지는
열을 **빈 칸으로 보고 화면 끝에서 멈췄습니다.** 3,000행 열의 A1 에서 누르면
A3000 이 아니라 A22 에 섰습니다.

이제 화면 안에서 답이 나지 않으면 편집기가 그 줄의 채워진 구간을 서버에
묻습니다. 서버는 64행 블록 단위로 읽고, 필요한 만큼만 읽으면 멈춥니다. 걷기
자체는 편집기가 하므로 **필터나 그룹으로 숨긴 행은 전처럼 건너뜁니다.** 막
입력해서 아직 저장되지 않은 칸도 채워진 칸으로 셉니다.

이번에 스프레드시트의 규칙도 맞췄습니다.

| 출발 | 전 | 이제 |
| --- | --- | --- |
| 데이터 덩어리 안 | 화면 끝에서 멈출 수 있음 | 그 덩어리의 마지막 칸 |
| 덩어리의 마지막 칸 | 그 자리에 그대로 | 다음 덩어리의 첫 칸, 없으면 시트 끝 |
| 빈 칸 | 데이터 바로 앞의 빈 칸 | 다음 데이터의 첫 칸, 없으면 시트 끝 |

연달아 누른 키는 차례로 처리되어, 두 번째 `Ctrl + ↓` 는 첫 번째가 도착한
자리에서 출발합니다. 서버 답을 기다리는 사이에 다른 칸을 누르면 그 클릭이
이깁니다. 서버에 닿지 못하면 화면에 있는 셀로 판단합니다.

새 REST 경로(`range.read`):

```
GET /api/v1/sheets/{sheetId}/cells/{A1}/edge?direction=up|down|left|right
GET /api/v1/sheets/{sheetId}/cells/{A1}/region
```

## MCP 로 셀·서식·자동화를 고칠 수 있습니다

### 쓰기 인수가 게이트웨이를 지나도 도착합니다

사내 MCP 게이트웨이는 도구의 `inputSchema` 에 적힌 인수만 kanpic 으로
넘깁니다. 그런데 `spreadsheet.range.write` 의 스키마에는 `sheet_id` 와
`idempotency_key` 만 있고 정작 쓸 내용인 `cells` 가 없었습니다.
`spreadsheet.formula.set` 도 `row`·`column`·`formula` 가 빠져 있었습니다.
그래서 게이트웨이를 거친 쓰기는 모두 이렇게 실패했습니다.

```
cells must contain 1 to 1000 entries
```

핸들러가 읽는 인수를 모두 스키마에 적었습니다. `cells` 는 항목마다 `row`·
`column`(1부터)·`value`·`formula`·`style`·`note` 를 갖는다고 적혀 있어, 모델도
무엇을 보내야 하는지 압니다. 같은 이유로 빠져 있던 것 — 정렬의
`header_rows`·`case_sensitive`, 시트 이름·순서·색상 변경, 차트의 보조 축·
데이터 레이블·축 범위, 레이아웃의 인쇄 영역·슬라이서, 가져오기의
`idempotency_key` 등 — 도 함께 적었고, 차트 유형(11가지)과 레이아웃 동작
(15가지)의 허용값 목록을 서버가 실제로 받는 값에 맞췄습니다.

게이트웨이가 흔히 바꾸는 꼴도 서버가 스키마에 맞춰 되돌립니다.

| 게이트웨이가 보낸 것 | 전 | 이제 |
| --- | --- | --- |
| `"arguments": "{\"sheet_id\":…}"` (객체를 문자열로) | 프로토콜 오류 | 객체로 읽음 |
| `"cells": "[{…}]"` (배열을 문자열로) | `cannot unmarshal string` | 배열로 읽음 |
| `"row": "3"` (숫자를 문자열로) | 거절 | 3 |
| `sheetId`, `idempotencyKey` (camelCase) | 인수 없음 | `sheet_id`, `idempotency_key` |
| `{"arguments": {…}}` (한 번 더 감쌈) | 인수 없음 | 안쪽 객체 |
| `idempotency_key` 없음, `Idempotency-Key` 헤더 있음 | 거절 | 헤더 값 |
| `idempotency_key` 도 헤더도 없음 | 거절 | 그 호출만의 키로 한 번 실행 |

스키마가 형식을 정하지 않은 셀 `value` 는 손대지 않으므로 `"0012"` 같은
글자는 글자로 남습니다. 재시도해도 한 번만 반영되기를 바라면 전처럼
`idempotency_key`(또는 헤더)를 보내세요 — 같은 키는 여전히 한 번만 씁니다.

### 자기 소유 워크북은 scope 를 기본으로 엽니다

MCP 연동 계정의 Keycloak 토큰이나 API 키는 `workbook.read` 처럼 좁혀져 있는
경우가 많습니다. 좁힌 이유는 남이 공유해 준 워크북을 에이전트가 고치지 못하게
하려는 것인데, 그 바람에 **그 사용자가 직접 만든 워크북**에도 셀 한 칸을 쓸
수 없었습니다. 쓰기 scope 를 받으려면 Keycloak Client Scope 를 새로 만들어
달라는 요청을 다른 팀에 넣어야 했습니다.

이제 호출이 가리키는 워크북의 **소유자가 그 키·토큰의 사용자**이면, 새 설정
`mcp.owner_scopes` 의 scope 가 그 호출에 한해 더해집니다. 기본값은 다음과
같습니다.

```
workbook.read
range.read  range.write      formula.read  formula.write
format.read format.write     automation.read automation.write automation.run
chart.read  chart.write      pivot.read    pivot.write
comment.read comment.write   version.read  version.write
```

접수된 `format.read`·`format.write`·`automation.read`·`automation.run`·셀 쓰기가
모두 들어 있습니다. 지켜지는 선은 그대로입니다.

- **남이 공유해 준 워크북**에서는 편집자여도 키·토큰의 scope 만 봅니다.
- 한 호출이 **둘 이상의 워크북**을 가리키면(내 시트와 남의 워크북을 함께 적는
  식) 더하지 않습니다.
- 관리자라서 생기는 소유자 권한은 소유로 치지 않습니다. 워크북의 실제
  소유자여야 합니다.
- 공유·소유권 이전·삭제(`workbook.write`), 관리(`admin.*`), API 키, 개인 설정,
  AI(`ai.use`), 가져오기, 웹훅은 이 설정에 **넣을 수 없습니다.** 저장할 때
  거절되고, 저장소에 들어 있어도 무시됩니다.
- 끄려면 `mcp.owner_scopes` 를 빈 목록으로 저장합니다. 설정을 읽지 못하는
  순간에는 아무것도 더하지 않습니다.

API 키와 Keycloak 토큰에 똑같이 적용되고, 처음부터 모든 scope 를 가진 키나
scope 가 실리지 않은 토큰에는 달라지는 것이 없습니다.

남이 공유해 준 워크북까지 MCP 로 쓰게 하려면 여전히 키·토큰에 scope 를
줘야 합니다. 이때 접수 문구 그대로 `spreadsheet.write` 를 Client Scope 이름으로
쓸 수 있습니다 — kanpic 은 이를 `range.write` + `formula.write` 로,
`spreadsheet.read` 를 `workbook.read` + `range.read` + `formula.read` 로 읽습니다.
보호 리소스 문서(`/.well-known/oauth-protected-resource/mcp`)의
`scopes_supported` 에도 두 이름이 실립니다.

## 그 밖에 바뀌는 것은 없습니다

- **마이그레이션은 없습니다.** 새 설정 `mcp.owner_scopes` 는 서버가 뜰 때 기본값으로
  들어갑니다. 필수 환경 변수는 계속 `POSTGRES_DSN` 하나입니다.
- 셀 저장 방식, 수식 엔진, 공유 규칙, REST 의 scope 판정은 바뀌지 않았습니다.
  소유 워크북 기본 scope 는 `/mcp` 에만 적용됩니다.
- 이미 필요한 인수를 다 보내던 MCP 클라이언트에는 달라지는 것이 없습니다.
  필수 인수가 늘어난 도구(`range.write|paste|fill` 의 `cells`, `formula.set` 의
  `row`·`column`·`formula`, `import.execute` 의 `idempotency_key`)는 전에도 그
  인수 없이는 실패하던 것들입니다.

## 올리실 때

v0.266.0 에서 올라오시는 분은 이미지를 바꿔 다시 띄우시면 됩니다.
마이그레이션은 없습니다.

- MCP 연동 계정이 자기 워크북만 다룬다면 Keycloak 쪽에서 할 일은 없습니다.
  공유받은 워크북까지 쓰게 하려면 Client Scope(`spreadsheet.write`,
  `format.read`, `format.write`, `automation.read`, `automation.run`)를 붙이세요.
- 소유 워크북 기본 허용을 원하지 않으면 **관리자 콘솔 › 시스템 설정**에서
  `mcp.owner_scopes` 를 빈 목록으로 저장합니다.
- `Ctrl + A` 를 처음 누르면 시트 전체가 아니라 데이터 표가 선택된다는 점을
  사용자분들께 알려 주세요. 한 번 더 누르면 전처럼 시트 전체입니다.

되돌리셔도 스키마는 그대로이므로 v0.266.0 이미지로 돌아갈 수 있습니다.
`mcp.owner_scopes` 설정은 남지만 v0.266.0 은 읽지 않습니다.
