## 릴리즈 요약

v0.112.0은 지난 릴리즈에서 **남겨 둔 절반**을 마저 합니다. 워크북 목록을 한 페이지씩 받고, 검색과 필터를 서버로 옮겼습니다. 워크북 5,119개에서 홈 화면의 첫 카드까지 **2.6초에서 0.23초로** 줄었습니다.

마이그레이션은 없습니다. 필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나입니다.

## 전부 받아서 브라우저에서 걸러 냈다

지난 릴리즈에서 서버 질의를 37배 빠르게 했지만, 목록은 여전히 **열 수 있는 워크북을 전부** 보냈습니다. 5,119개면 3.26MB이고 브라우저는 카드를 5,119개 그립니다. 화면의 필터(내 소유·공유됨·즐겨찾기)도 그 전부를 받아 놓고 브라우저에서 걸러 내는 방식이었습니다.

이제 한 번에 **60개**씩 받고, 필터도 서버가 겁니다.

| 워크북 5,119개 | 이번 세션 시작 | N+1 고친 뒤 | 지금 |
| :--- | :--- | :--- | :--- |
| 목록 응답 | 1.78초 / 3.26MB | 0.048초 / 3.26MB | **0.011초 / 38KB** |
| 첫 카드까지 | 3.9초 | 2.6초 | **0.23초** |
| 그려지는 카드 | 5,119개 | 5,119개 | **60개** |

## 페이지를 나누면 찾을 수 없게 된다

그래서 **검색을 함께 넣었습니다.** 목록 위 검색 상자에 이름 일부를 넣으면 서버가 제목으로 찾습니다. 5,000개 중 4,987번째 워크북도 이름으로 바로 나옵니다. 나누기만 하고 찾을 방법을 주지 않으면 첫 페이지 밖의 워크북은 없는 것이나 마찬가지가 됩니다.

**더 보기** 로 다음 60개를 이어 봅니다. 남은 개수도 함께 보여 줍니다.

제목에 든 `%` 나 `_` 는 글자 그대로 찾습니다. 검색 문법의 기호로 새어 들어가면 `%` 하나가 모든 워크북과 맞아 버립니다.

## 기존 호출은 그대로

`limit` 을 주지 않으면 예전처럼 전부 돌려줍니다. 워크북을 가로질러 계산하는 수식과 MCP 도구가 전체 목록을 필요로 하기 때문입니다. 응답에 `total` 과 `has_more` 가 늘었을 뿐, 기존 필드는 그대로입니다. 한 페이지는 최대 500개로 끊습니다.

## 검증 결과

- 메모리 저장소와 PostgreSQL 저장소에 **같은 경우들**을 각각 물었습니다. 화면이 둘 중 어느 쪽을 쓰든 같은 답을 내야 합니다. 페이지를 이어 붙이면 전체 목록과 순서까지 같고, 빠지거나 겹치는 워크북이 없습니다. 마지막 페이지는 "더 없음" 이라고 답합니다.
- 검색이 대상 밖을 넘지 않는지, `%` 와 `_` 가 글자로 다뤄지는지, 검색과 페이지를 함께 쓸 때 전체 수가 검색 결과의 수인지 봅니다.
- 브라우저 E2E로 첫 페이지가 60개 이하인지, 이름으로 찾으면 그 워크북만 나오는지, 없는 이름에는 그렇게 말하는지, 검색을 지우면 목록이 돌아오는지 봅니다.
- 만들다 걸린 것: 검색 디바운스가 화면이 열린 직후에도 돌면서 방금 누른 **더 보기** 를 되돌렸습니다. 검색어가 실제로 바뀔 때만 첫 페이지로 돌아가게 고쳤고, E2E가 이것을 잡았습니다.
- `go vet ./...`, `go test ./...`, PostgreSQL 통합 테스트, React/Vitest, TypeScript 타입 검사, Vite 프로덕션 빌드, Playwright E2E를 통과했습니다.
