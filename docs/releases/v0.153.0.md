## 릴리즈 요약

v0.153.0은 v0.152.0이 연 길의 **돌아오는 쪽** 을 냅니다. 이름 있는 수식을 엑셀 `LAMBDA` 로 내보내게 했는데, 가져오는 쪽은 그것을 버리고 있었습니다. 나갔다 들어오며 사라지면 내보낸 것이 원본 구실을 하지 못합니다.

## 내보낸 파일을 도로 열면 이름이 그대로 있습니다

```
_xlfn.LAMBDA(매출,원가,(매출-원가)/매출)
  -> 마진율(매출, 원가) = (매출-원가)/매출
```

마지막 인자가 본문이고 그 앞이 매개변수입니다. 본문 안에도 쉼표가 있으므로 **괄호와 따옴표 밖의 쉼표에서만** 자릅니다. 본문의 `_xlfn` 은 벗깁니다.

이름 범위와 같이 **첫 계산 전에** 넣습니다. 늦게 넣으면 그 이름을 부르는 칸이 `#NAME?` 으로 굳고, 나중에 이름을 다시 만들어도 굳은 값은 돌아오지 않습니다.

## 부르는 법이 파일을 건너며 달라지지 않습니다

매개변수가 없는 이름도 이제 `LAMBDA` 로 감싸 내보냅니다. 값만 적으면 엑셀에서는 `기준연도`, kanpic 에서는 `기준연도()` 가 되어 수식을 손봐야 하고, 그러면 도로 가져올 때 이름 있는 수식이 아니라 상수가 됩니다.

## 일부러 그대로 둔 것

값이나 범위를 가리키는 **보통의 정의된 이름은 이름 있는 수식으로 담지 않습니다.** 담으면 엑셀에서 `=A1*세율` 이던 것이 kanpic 에서 `세율()` 이 되어, 수식은 여전히 깨지는데 **알리지도 않게** 됩니다. 지금처럼 가져오기 요약에서 세어 알리면, 사람이 그것을 다시 만들지 말지 정할 수 있습니다. 조용히 깨지는 것이 가장 나쁩니다.

## CI 가 이따금 빨갛던 까닭

통합 시험을 여섯 번쯤 돌리면 한 번 예정 자동화 시험이 실패했습니다. 잡아 보니 결과가 둘이었고 워크북 ID 가 서로 달랐습니다.

예정 실행을 쓸어 담는 일은 데이터베이스 전체를 훑는 것이 맞습니다 — 스케줄러는 워크북 하나를 위해 도는 것이 아닙니다. 그런데 시험들이 데이터베이스 하나를 나눠 쓰고 나란히 돌므로, **남의 워크북 자동화가 같은 순간에 걸리면 섞여 들어옵니다.** 만든 코드가 아니라 시험이 스케줄러를 혼자 쓴다고 여긴 것이 틀렸습니다. 자기 워크북의 결과만 세도록 다섯 자리를 고쳤습니다.

빨갛게 되는 까닭이 만든 것에 없으면 사람은 CI 를 믿지 않게 되고, 정작 진짜로 빨간 날을 흘려보내게 됩니다.

## 검증 결과

- 나갔다 들어오는 길 전체를 봅니다. 이름이 셋 다 돌아오고, 이름을 부르는 칸이 `0.4` 로 다시 계산되고, 되살린 이름을 버렸다고 알리지 않는지.
- 쉼표를 가진 본문(`IFS(b=0,0,TRUE,a/b)`)과 매개변수 없는 이름을 함께 확인합니다.
- 실패를 되살려 낸 뒤, 같은 조건에서 통합 시험 전체를 네 번 더 돌려 확인했습니다.
- Go 시험 전체와 통합 시험 전체가 통과합니다.
