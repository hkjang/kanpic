## 릴리즈 요약

v0.18.0은 외부 업무 시스템이 kanpic 자동화를 안전하게 시작할 수 있는 **API 키 인증 인바운드 웹훅 트리거**를 추가합니다. 웹훅 호출은 전용 최소 scope와 멱등 키가 필수이며, 전달된 JSON 원문을 PostgreSQL이나 로그에 저장하지 않고 SHA-256·크기·호출 키 ID만 감사 정보로 보존합니다.

필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나입니다. Redis, 별도 webhook gateway, 메시지 브로커와 외부 인터넷 연결 없이 폐쇄망에서 동작하며, 기존 개인 API 키의 생성·조회·수정·폐기·회전 체계를 그대로 사용합니다.

## 핵심 변경

- 워크북 자동화 trigger에 `webhook`을 추가했습니다. 기존 값 설정, 상대 수식 적용과 내용 지우기 작업을 외부 JSON 이벤트로 시작할 수 있습니다.
- 각 웹훅 자동화는 `POST /api/v1/automations/{automationId}:webhook` endpoint를 사용합니다.
- 웹훅 endpoint는 로그인 세션이나 개발용 `X-Kanpic-Actor`를 허용하지 않고 반드시 개인 API 키 Bearer 인증을 요구합니다.
- 호출 키에는 `automation.webhook.invoke` scope가 필요합니다. `automation.*` wildcard도 기존 scope 규칙에 따라 이를 포함합니다.
- 모든 전달에 `Idempotency-Key` HTTP header가 필요합니다. 원본 시스템의 이벤트 ID를 사용하면 응답 유실이나 네트워크 재시도에서도 작업을 한 번만 반영합니다.
- payload는 비어 있거나 최대 1MiB의 유효한 JSON이어야 하며 잘못된 JSON은 `400`, 초과 payload는 `413`으로 거부합니다.
- 예약 실행 조회는 활성 워크북과 결합됩니다. soft-delete된 워크북에 남은 과거 예약 정의를 실행하거나 반복 오류로 기록하지 않습니다.

## 데이터 최소화와 감사

- webhook payload 원문은 `automation_runs`, 셀 스냅샷, 작업 로그, 감사 로그와 구조화 서버 로그에 기록하지 않습니다.
- 원본 바이트의 SHA-256 digest와 byte 수만 실행 이력에 저장해 같은 payload 여부와 전달 규모를 검증할 수 있습니다.
- 실행을 시작한 개인 API 키 UUID를 `trigger_key_id`로 저장합니다. 원문 키나 SHA-256 키 hash는 자동화 이력에 복제하지 않습니다.
- 키 UUID는 `api_keys`를 참조하며 키를 회전·폐기해도 과거 호출자를 감사할 수 있습니다. 키 레코드가 삭제되는 경우 실행 이력의 참조는 안전하게 `NULL` 처리됩니다.
- 성공·변경 없음·실패 감사 이벤트에는 자동화 ID, trigger 유형, 기준 버전, payload digest·크기와 키 ID가 포함됩니다.
- 관리자 서버 로그에는 endpoint, trace ID, 실행 ID와 결과를 남기되 request body는 기록하지 않습니다.

## 멱등성 및 서버 권위 실행

- 같은 사용자·자동화·`Idempotency-Key` 조합을 재전송하면 첫 번째 실행 결과를 `duplicate=true`로 반환합니다.
- 재전송 payload가 달라도 기존 멱등 키의 첫 실행 digest와 결과가 권위값입니다. 발신자는 서로 다른 원본 이벤트에 같은 키를 재사용하면 안 됩니다.
- 유효한 웹훅은 기존 자동화 실행 한도, 정의 활성 상태, 작업 셀 수, 최신 워크북 버전과 대상 셀 기대값을 모두 검사합니다.
- 셀 작업은 일반 편집과 같은 PostgreSQL 트랜잭션 경로에서 원자적으로 반영되며 수식 재계산, 워크북 버전, 작업 로그와 WebSocket 협업 전파를 포함합니다.
- 대상 셀이 이미 원하는 상태면 webhook 호출 자체는 성공으로 수락하되 워크북 버전을 만들지 않고 `skipped` 실행으로 기록합니다.
- 성공한 셀 작업은 기존 실행 이력에서 Undo할 수 있으며 이후 다른 사용자가 같은 셀을 바꾼 경우 안전하게 거부합니다.
- 워크북별 시간당 실행 제한에는 webhook 실행도 포함되므로 과도한 외부 호출은 `429`로 차단됩니다.

## 개인 API 키 운영

- `/preferences`의 API 키 scope 선택에 `automation.webhook.invoke`를 추가했습니다.
- 웹훅 전용 키에는 가능하면 `automation.webhook.invoke`만 부여하고 정의 변경이나 워크북 조회 scope를 함께 주지 않는 것을 권장합니다.
- 키 원문은 생성 또는 회전 직후 한 번만 반환되며 데이터베이스에는 SHA-256 hash만 저장됩니다.
- 키 회전은 기존 키를 즉시 폐기하고 같은 이름·scope·만료 정책의 새 키를 발급합니다. 외부 호출 시스템의 Secret Manager 값을 함께 교체해야 합니다.
- 만료되었거나 폐기·회전된 키의 웹훅 호출은 `401 Unauthorized`로 거부됩니다.
- 관리자 `/admin`의 전체 API 키 현황에서는 원문을 노출하지 않고 소유자, prefix, scope, 만료·최근 사용·폐기 상태를 확인할 수 있습니다.

## REST API

```http
POST /api/v1/automations/{automationId}:webhook
Authorization: Bearer kp_live_...
Idempotency-Key: source-event-20260802-001
Content-Type: application/json

{"event":"approved","request_id":"REQ-001"}
```

- 성공 응답은 기존 `AutomationExecutionResult`이며 `run.trigger_type=webhook`을 반환합니다.
- 실행 이력의 `trigger_key_id`, `payload_digest`, `payload_bytes`로 호출 메타데이터를 확인할 수 있습니다.
- API 키가 없으면 `api_key_required`, scope가 부족하면 `insufficient_scope`, 멱등 header가 없거나 200자를 넘으면 `invalid_idempotency_key`, JSON Content-Type이 아니면 `unsupported_media_type` 오류를 반환합니다.
- trigger가 `webhook`이 아닌 자동화 ID를 호출하면 서버 검증이 요청을 거부합니다.

## MCP 도구

- `spreadsheet.automation.webhook.invoke`를 추가했습니다.
- 입력은 `automation_id`, `idempotency_key`, 선택적 `client_id`와 임의 JSON `payload`입니다.
- MCP를 통한 호출도 `/mcp` 자체의 `mcp.use`와 도구의 `automation.webhook.invoke` scope, 개인 API 키 인증을 모두 요구합니다.
- MCP Gateway는 payload를 JSON으로 직렬화한 후 REST와 같은 1MiB 한도와 SHA-256 최소 보존 정책을 적용합니다.
- 정의 생성·수정의 trigger schema에도 `webhook` enum을 추가해 에이전트가 화면과 동일한 자동화를 만들 수 있습니다.

## 편집기

- 자동화 폼의 실행 조건에 **인바운드 웹훅**을 추가했습니다.
- 웹훅을 선택하면 개인 API 키 scope, 필수 `Idempotency-Key`와 payload 비보존 정책을 폼 안에서 안내합니다.
- 저장된 자동화 카드에 실제 `POST /api/v1/automations/{id}:webhook` 경로를 표시합니다.
- 실행 이력에는 payload byte 수와 SHA-256 앞부분을 표시하고 원문은 표시하지 않습니다.
- webhook 정의도 저장 직후 현재 서버 셀 기준의 쓰기 없는 미리보기를 제공하므로 외부 시스템에 endpoint를 연결하기 전에 변경 범위를 확인할 수 있습니다.

## PostgreSQL 마이그레이션

- `017_webhook_automations.sql`이 `automation_runs.trigger_key_id`, `payload_digest`, `payload_bytes`를 추가합니다.
- trigger 제약에 `webhook`을 추가하고 payload 크기를 0~1,048,576 byte로 제한하는 DB CHECK를 적용합니다.
- 키별 실행 감사를 위한 부분 인덱스를 추가합니다.
- 애플리케이션 시작 시 기존 자동 마이그레이션 체계가 `017`을 적용하며 별도 수동 DDL이 필요하지 않습니다.
- 관리자 **저장소 준비 상태 테스트**는 예약 컬럼과 함께 웹훅 키·digest·크기 컬럼도 실제로 조회합니다.

## 검증 결과

- `go test ./...`와 `go vet ./...`를 통과했습니다.
- HTTP 보안 계약 테스트에서 API 키 필수, 전용 scope, 멱등 header, invalid JSON과 1MiB 초과 거부, digest·키 ID 전달을 검증했습니다.
- 실제 PostgreSQL 17의 호스트 5432 포트를 사용하는 전체 통합 테스트를 통과했습니다. webhook 정의, 성공·변경 없음, 재전송 중복 제거, API 키 외래 키, 감사 metadata, payload 원문 비보존과 삭제된 워크북 예약 제외를 확인했습니다.
- REST scope와 MCP 도구 metadata·입력 schema 계약을 검증했습니다. 인증 없는 MCP webhook 호출도 도구 오류로 거부됩니다.
- React/Vitest 19개 테스트 파일, 66개 테스트를 통과했습니다. webhook trigger 생성 안내와 endpoint 표시를 포함합니다.
- TypeScript 타입 검사와 Vite 프로덕션 빌드를 통과했습니다.
- Playwright E2E 31건을 통과했습니다. 실제 브라우저와 PostgreSQL에서 전용 API 키 생성, 인증 없는 호출 거부, webhook 실행, 재전송 중복 제거, 이력 조회, 키 폐기 후 차단과 전체 기존 기능 회귀를 확인했습니다.
- 릴리즈 Docker 이미지는 PostgreSQL 전용 구성으로 자동 `017` 마이그레이션, `/healthz`, `/api/v1/version`, 오프라인 `docker load`와 SHA-256 무결성을 검증합니다.

## 업그레이드 참고

- v0.17.0 이하에서 시작하면 `017_webhook_automations.sql`이 자동 적용됩니다. 운영 업그레이드 전 PostgreSQL 백업을 권장합니다.
- 기존 수동·셀 변경·Cron 자동화와 실행 이력은 그대로 호환되며 새 컬럼은 기존 행에서 빈 값 또는 `NULL`입니다.
- 기존 개인 API 키에는 `automation.webhook.invoke`가 자동 추가되지 않습니다. webhook 발신 시스템마다 최소 scope의 새 키를 만들거나 명시적으로 기존 키 scope를 수정하십시오.
- webhook 실행은 `automation.enabled` 정책과 기존 셀·시간당 실행 한도를 따릅니다. 관리자 화면에서 정책 검증과 저장소 준비 상태 테스트를 먼저 수행하십시오.
- 필수 런타임 환경 변수는 `POSTGRES_DSN` 하나이고 PostgreSQL 기본 포트 예시는 5432입니다.

## 현재 지원 범위와 다음 단계

- 이번 버전의 webhook은 외부 시스템에서 kanpic 자동화를 시작하는 **인바운드 trigger**입니다.
- kanpic이 외부 URL을 호출하는 아웃바운드 webhook action은 아직 제공하지 않습니다.
- 아웃바운드 호출은 사설·loopback·metadata 주소 차단, DNS rebinding 방어, 관리자 도메인 허용 목록, Secret Manager 참조, timeout, durable retry와 Dead Letter Queue를 함께 구현한 뒤 활성화할 예정입니다.
