## 릴리즈 요약

v0.103.0은 **숫자가 이상하게 보이던 세 가지**를 고칩니다. `=0.1+0.2` 를 넣어 보다 찾았습니다.

마이그레이션은 없습니다. 필수 런타임 환경 변수는 계속 `POSTGRES_DSN` 하나입니다.

## 0.1 더하기 0.2가 0.3이 아니었다

`=0.1+0.2` 의 결과가 `0.30000000000000004` 였습니다. `=1.1*3` 은 `3.3000000000000003`, `=SUM(0.1,0.2,0.3)` 은 `0.6000000000000001` 이었습니다.

컴퓨터가 이 소수들을 2진수로 정확히 담지 못해 생기는 나머지입니다. 어느 스프레드시트에서나 같은 방법으로 감춥니다 — 결과를 **유효숫자 15자리**로 정리하는 것으로, 64비트 실수가 정확히 약속할 수 있는 한계이기도 합니다. 엑셀과 구글 시트도 같은 자리를 씁니다.

이제 `=0.1+0.2` 는 `0.3`, `=1/3` 은 `0.333333333333333` 입니다.

## 대조 수식이 없는 불일치를 알렸다

`=0.1+0.2=0.3` 이 **FALSE** 였습니다. 보이는 문제로 끝나지 않습니다. `=IF(합계=예상,"OK","불일치")` 처럼 두 값을 맞춰 보는 수식이 멀쩡한 표를 두고 불일치를 보고합니다.

비교도 같은 자리에서 하도록 했습니다. 이제 TRUE 입니다.

## 지수 표기를 수식에서 쓸 수 없었다

`=1E-10`, `=2E3`, `=1.5E+3` 이 전부 `#ERROR!: unexpected token "E"` 였습니다. 값으로 `1.5e3` 을 치면 1500으로 받으면서 수식 안에서는 못 읽었습니다. 아주 크거나 작은 수를 다루면 바로 막힙니다.

이제 읽습니다. `E` 뒤에 숫자가 오지 않으면 셀 참조이므로 `=SUM(A1:E3)` 와 `=A1*E3` 는 그대로입니다.

## 빈 응답으로 돌아오던 오버플로

`=1E308*10` 은 무한대가 되는데, 무한대는 JSON으로 쓸 수 없습니다. 서버가 200과 함께 **빈 본문**을 보내고 브라우저는 응답을 해석하지 못했습니다. 지수 표기를 받게 되면서 훨씬 쉽게 닿는 자리가 되었으므로 함께 고쳤습니다. 이제 `#NUM!` 입니다. 배열 결과 안에 섞여 있어도 같습니다.

## 검증 결과

- 단위 테스트 세 가지를 남겼습니다. 열다섯 자리 정리와 비교(11가지 식), 지수 표기와 `E3` 참조 구분(8가지 식), 오버플로가 `#NUM!` 이면서 JSON으로 쓸 수 있는지 확인합니다.
- 고치기 전 엔진에서 세 가지가 모두 실패하는 것을 확인했습니다.
- 브라우저 E2E로 실제 시트에서 `=SUM(A1:A2)` 가 0.3이 되고 `=IF(A3=0.3,…)` 이 "맞음"을 내는지 봅니다.
